### 📋 HU-14: Procesamiento Transaccional de Checkout y Pedidos Atómicos

**Como** Cliente autenticado de SneakerHub Ayacucho  
**Quiero** consolidar los artículos de mi carrito de compras seleccionando una de mi direcciones urbanas registradas para emitir una orden de compra formal  
**Para** asegurar la adquisición de mis zapatillas, garantizar el bloqueo físico del inventario y programar el despacho de la mercancía a domicilio.

---

#### 📌 1. Precondiciones y Postcondiciones
* **Precondiciones:**
  1. El cliente debe estar autenticado con un token JWT vigente bajo el guardián de sesión `verificar_usuario`.
  2. La dirección de entrega (`direccion_id`) provista debe existir en MySQL y pertenecer legítimamente al usuario autenticado (HU-10).
  3. Los productos y las tallas seleccionadas deben contar con existencias físicas en el momento exacto del procesamiento.
* **Postcondiciones:**
  1. Se genera una fila matriz en la tabla `pedidos` y múltiples tuplas hijas en la tabla de auditoría `detalles_pedido`.
  2. El stock de la tabla `tallas_stock` se debita de forma atómica.
  3. Se limpia el estado de selección en el entorno frontend del cliente al recibir la confirmación síncrona.

---

#### 🛠️ 2. Criterios de Aceptación Técnicos Detallados
* **CA-01 (Seguridad Multinquilino):** El endpoint requiere obligatoriamente una firma JWT válida. El backend debe comprobar que el `direccion_id` enviado pertenezca al ID del usuario extraído del token. Intentos de inyección de direcciones ajenas abortarán la operación con un código **403 Forbidden**.
* **CA-02 (Garantía de Atomicidad ACID contra Condiciones de Carrera):** Para evitar inconsistencias de inventario por compras concurrentes masivas, el proceso de Checkout debe ejecutarse dentro de un bloque transaccional unificado en el motor InnoDB de MySQL. Si cualquiera de los artículos de la lista sufre un quiebre de stock inesperado durante el bucle de procesamiento, el backend invocará de forma inmediata la instrucción `db.rollback()`. Esto revertirá cualquier inserción previa o alteración física del inventario, garantizando un estado íntegro y respondiendo un **409 Conflict**.
* **CA-03 (Invariante Financiera y Cálculo Total Autónomo):** El backend ignorará por completo cualquier subtotal monetario provisto por el cliente frontend. Los precios netos y el monto global acumulado de la orden de compra se calcularán síncronamente en el servidor extrayendo las tarifas base y las reglas de descuento vigentes de la tabla `productos` en MySQL.
* **CA-04 (Congelamiento de Precios Históricos):** El precio de venta asentado en la tabla `detalles_pedido` debe fijarse como un valor estático e inmutable en el instante del checkout. Esto aislará el registro de auditoría de futuras modificaciones en el catálogo o alteraciones promocionales de la plataforma (HU-12).

#### 📊 3. Esquemas de Validación y Contratos de Datos (Pydantic)

```python
from pydantic import BaseModel, Field
from typing import List

# Payload de Entrada: Estructura enviada por el formulario de checkout web
class ItemPedidoInput(BaseModel):
    producto_id: int = Field(..., description="ID del calzado a comprar")
    talla: str = Field(..., description="Talla comercial seleccionada")
    cantidad: int = Field(..., ge=1, description="Cantidad de pares a adquirir")

class CheckoutPayload(BaseModel):
    direccion_id: int = Field(..., description="ID de la dirección de entrega urbana del cliente")
    items: List[ItemPedidoInput] = Field(..., min_length=1, description="Arreglo de artículos de la orden")

# Esquemas de Salida: Confirmación estructurada de la orden asentada
class DetallePedidoResponse(BaseModel):
    id: int
    producto_id: int
    talla: str
    cantidad: int
    precio_unitario_historico: float

    class Config:
        from_attributes = True

class PedidoResponse(BaseModel):
    id: int = Field(..., description="ID de la orden transaccional generada")
    usuario_id: int
    direccion_id: int
    monto_total: float = Field(..., description="Monto neto final facturado y calculado por el servidor")
    estado_pago: str = Field(..., description="Por defecto: PENDIENTE_VERIFICACION")
    items_facturados: List[DetallePedidoResponse] = []

    class Config:
        from_attributes = True
```

#### 🗄️ 5. Implementación del Algoritmo del Controlador (`backend/app/routers/orders.py`)

```python
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy.orm import Session, joinedload
from app.database import get_db
from app.models.user import Usuario, DireccionEntrega
from app.models.product import Producto
from app.models.variant import TallaStock, VarianteColor
from app.models.order import Pedido, DetallePedido  # Mapeo del modelo order.py
from app.schemas.order import CheckoutPayload, PedidoResponse, DetallePedidoResponse
from app.routers.auth import verificar_usuario

router = APIRouter(prefix="/api/orders", tags=["Órdenes y Pedidos"])

@router.post(
    "/checkout", 
    status_code=status.HTTP_201_CREATED, 
    response_model=PedidoResponse,
    summary="Procesamiento transaccional de checkout e inyección de pedido (Atómico)"
)
def procesar_checkout_transaccional(
    payload: CheckoutPayload,
    db: Session = Depends(get_db),
    usuario_actual = Depends(verificar_usuario)
):
    # 1. Recuperar la identidad del inquilino autenticado por JWT
    user = db.query(Usuario).filter(Usuario.email == usuario_actual.email).first()

    # 2. Validar propiedad y existencia de la dirección de despacho urbana
    direccion = db.query(DireccionEntrega).filter(
        DireccionEntrega.id == payload.direccion_id,
        DireccionEntrega.usuario_id == user.id
    ).first()
    
    if not direccion:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="Violación de Seguridad: La dirección de entrega no existe o no pertenece a su cuenta."
        )

    # 3. Inicializar la cabecera de la orden ORM antes del procesamiento de líneas
    nuevo_pedido = Pedido(
        usuario_id=user.id,
        direccion_id=payload.direccion_id,
        monto_total=0.0,
        estado_pago="PENDIENTE_VERIFICACION"
    )
    
    # Abrimos explícitamente el hilo de persistencia atómica en MySQL
    db.add(nuevo_pedido)
    db.flush()  # Genera el ID transaccional de la cabecera sin hacer commit definitivo

    monto_acumulado_total = 0.0
    lineas_facturadas_orm = []

    try:
        # 4. Procesar y auditar cada ítem secuencialmente bajo el aislamiento InnoDB
        for item in payload.items:
            # Extraer el calzado base verificando que se encuentre comercialmente ACTIVO
            producto = db.query(Producto).filter(Producto.id == item.producto_id, Producto.estado == "ACTIVO").first()
            if not producto:
                raise HTTPException(
                    status_code=status.HTTP_400_BAD_REQUEST,
                    detail=f"Catálogo Alterado: El calzado con ID #{item.producto_id} ya no está disponible."
                )

            # Buscar la celda física de inventario para la talla solicitada
            celda_inventario = db.query(TallaStock).join(VarianteColor).filter(
                VarianteColor.producto_id == producto.id,
                TallaStock.talla == item.talla
            ).with_for_update().first()  # Aplica bloqueo de fila en MySQL para evitar colisiones concurrentes

            # 5. Control de Suficiencia Numérica de Stock en Tiempo Real
            if not celda_inventario or celda_inventario.stock < item.cantidad:
                raise HTTPException(
                    status_code=status.HTTP_409_CONFLICT,
                    detail=f"Quiebre de Almacén: Stock insuficiente para {producto.nombre} en talla {item.talla}."
                )

            # 6. Calcular el precio neto con regla promocional del servidor
            descuento = producto.porcentaje_descuento if producto.porcentaje_descuento else 0.0
            precio_neto_historico = producto.precio_base * (1.0 - (descuento / 100.0))
            
            # Debitar de forma física e inmediata el inventario en MySQL
            celda_inventario.stock -= item.cantidad

            # 7. Instanciar la línea hija de auditoría estática
            detalle_linea = DetallePedidoResponse(
                id=0, # Autoincremental
                producto_id=producto.id,
                talla=item.talla,
                cantidad=item.cantidad,
                precio_unitario_historico=round(precio_neto_historico, 2)
            )
            
            linea_orm = DetallePedido(
                pedido_id=nuevo_pedido.id,
                producto_id=producto.id,
                talla=item.talla,
                cantidad=item.cantidad,
                precio_unitario_historico=round(precio_neto_historico, 2)
            )
            
            db.add(linea_orm)
            monto_acumulado_total += precio_neto_historico * item.cantidad
            lineas_facturadas_orm.append(linea_orm)

        # 8. Consolidar montos y asentar la transacción de forma definitiva (COMMIT)
        nuevo_pedido.monto_total = round(monto_acumulado_total, 2)
        db.commit()
        
        # Refrescar para hidratar el árbol relacional completo de salida
        db.refresh(nuevo_pedido)
        return nuevo_pedido

    except HTTPException as http_exc:
        db.rollback()  # Revierte absolutamente todo el proceso liberando los bloqueos físicos
        raise http_exc
    except Exception as e:
        db.rollback()
        raise HTTPException(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            detail=f"Fallo crítico transaccional en el motor relacional InnoDB: {str(e)}"
        )
```
